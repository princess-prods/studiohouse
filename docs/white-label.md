# White-label apps

A white-label app is one codebase that serves any brand. Which brand it serves is
decided by configuration, not by code, so adding a brand never means forking an app.

## How an app knows its brand

Resolution order, first match wins:

1. **Build-time config.** `BRAND` environment variable or an Angular `environment` file selected at build (`nx build brand-site --configuration=<brand>`). Use this when each brand gets its own deployment.
2. **Runtime host lookup.** The app reads `window.location.hostname` and matches it against the domains stored on the `brands` table. Use this when one deployment serves several domains.
3. **Explicit selection.** The CMS uses a brand switcher in its shell and passes the chosen `brand_id` on every request. This is how one admin app updates every brand.

## What switches per brand

| Concern                 | Mechanism                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Colours, fonts, spacing | A `ColorTheme` (five roles: primary, ink, paper, secondary, tint; optional success/warning/danger/info and fonts) from `@studiohouse/ui` is applied with `provideColorTheme()` / `ColorThemeService.set()`, which writes `--brand-*` and `--font-*` variables that `theme.css` maps onto every Spartan token and Tailwind utility. Components never hard-code colours. |
| Logo, favicon, copy     | Values on the brand record, served by the API and cached in the app.                                                                                                                                                                                                                                                                                                   |
| Feature flags           | JSON `features` column on the brand record; a `hasFeature('x')` helper gates UI.                                                                                                                                                                                                                                                                                       |
| Data                    | Every API request carries the brand id; the backend filters by `brand_id`.                                                                                                                                                                                                                                                                                             |
| Routing                 | Shared routes; per-brand routes are enabled by feature flags rather than separate route files.                                                                                                                                                                                                                                                                         |

## Product theme versus brand theme

Studiohouse itself has a theme (`STUDIOHOUSE_THEME`: Midnight, Champagne, Amber, Rosewood, Taupe; Sage, Mist for status; Playfair Display and Inter). Two rules keep the two kinds apart:

- **The CMS shell wears the product theme.** Sidebar, top bar, navigation and page chrome are always Studiohouse, whichever studio or brand is selected. Dark mode is the default.
- **Brand themes are scoped.** Anything that previews or edits a brand's content is wrapped in `[shBrandTheme]="brand.theme"`, which applies that brand's variables to that subtree only. `theme.css` resolves every token from `--brand-*`, so the subtree re-themes without any component knowing which brand it is rendering.

White-label apps are the opposite: they apply the brand's theme at the root with `provideColorTheme()` and never show the product theme.

## Where the code lives

- `packages/shared/ui` — `ColorTheme` model, `PRINCESS_PRODUCTIONS_THEME`, `ColorThemeService`, and `theme.css`. Tagged `scope:shared,type:ui`.
- `packages/shared/ui-helm` — Spartan helm primitives (button, card, input, label so far), generated by `@spartan-ng/cli:ui`.
- `packages/shared/db` — `studios`, `brands`, `color_themes` and related tables. See [database.md](./database.md).
- `packages/shared/brands` (planned) — `BrandService` (resolves the active brand, loads its theme into `ColorThemeService`), `hasFeature` helper. Tagged `scope:shared` so every app can use it.
- Each white-label app under `apps/` imports that library and contains only layout, pages and brand-agnostic components.
- Brand-specific assets (logos, hero imagery) are stored in object storage and referenced by URL from the brand record, never bundled into the app.

## Rules

- No `if (brand === 'brand-x')` in application code. If two brands need different behaviour, model it as a feature flag or a theme token.
- Theme tokens are data. Designers change a brand's look by editing its record in the CMS, not by editing CSS.
- Playwright e2e suites for white-label apps run once per brand configuration in CI so a theme change cannot break one brand silently.
